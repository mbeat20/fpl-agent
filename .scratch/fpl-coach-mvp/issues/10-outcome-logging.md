# 10 — Outcome logging

**What to build:** Per ADR-0012, record the real-world outcome of each Creator Stance and Recommendation once it's known — next gameweek's price movement, points scored, whether a captain pick paid off — sourced from data already pulled during a later ingestion cycle (ticket 03). Nothing reads this data in v1; it exists so v2's accuracy scoring (ADR-0001) has history to compute from instead of starting cold.

**Blocked by:** 03 — Real FPL API ingestion, 06 — Creator ingestion + extraction + trust tiers

**Status:** done

- [x] Each Recommendation made is stored with enough identity (player, pick, gameweek) to later match it against what actually happened
- [x] Each Creator Stance made is stored with enough identity to later match it against what actually happened
- [x] A subsequent ingestion cycle updates prior Recommendations and Creator Stances with their now-known outcome (price movement, points scored, captain result)
- [x] Outcome fields are populated without anything in v1 reading or acting on them

## Comments

**2026-08-18:** `recommendation_log` (new table) and `creator_stances` (extended with `gameweek`/`outcome_*` columns) both carry `gameweek`, a best-effort `player_id`/`fpl_player_id` (no FK, same wholesale-refresh convention as `players.fpl_element_id`), and nullable `outcome_price_change`/`outcome_points`/`outcome_recorded_at`. `outcomes.py`: `log_recommendation` (called from `routes.py`'s `ask()` right after `reasoning.reason()` returns) and `record_pending_outcomes` (called from `pipeline.py`'s `run_ingestion`, right after it resolves `elements_by_id`/`gameweek`).

`record_pending_outcomes` only ever fills in a row from *exactly* `gameweek - 1`, not "any earlier gameweek." bootstrap-static's `cost_change_event`/`event_points` are only ever "this event"'s numbers — writing them onto a row two-plus gameweeks stale (ingestion is on-demand per ADR-0002, so a cycle can be skipped) would silently record the *wrong* gameweek's numbers as if they were that pick's outcome, which is worse than leaving it NULL. A skipped cycle means that row's outcome is permanently unrecorded — an accepted v1 gap, not a bug, and worth knowing if v2 ever asks "why is this history so sparse."

Captain pay-off has no separate column: `outcome_points` read in context (a `creator_stances.stance = 'captain'` row, or a Recommendation known to have been a captaincy question) *is* whether it paid off — v1 only needs the raw fact recorded, not the interpretation, per AC4.

**Found and fixed a real bug while building this, not a hypothetical:** `run_ingestion` did `DELETE FROM teams WHERE id = %s` then re-`INSERT`ed it every cycle (to reset `players` wholesale via the FK cascade). Since `gameweek_state`/`instincts` are also FK'd to `teams(id) ON DELETE CASCADE`, that delete was silently wiping **every** Instinct — including current-gameweek ones ticket 13's purge logic was never meant to touch — on every single ingestion cycle. No test caught it because every test that seeded an Instinct did so *after* the fixture created the team, never *before* a `run_ingestion` call. `recommendation_log` hit the identical cascade and made the bug impossible to ignore: outcome history requires a row to survive the *next* ingestion cycle, which it never did. Fixed by upserting the `teams` row (`ON CONFLICT (id) DO UPDATE SET name = ...`) instead of delete+insert, with `players` now wholesale-replaced via its own explicit `DELETE FROM players WHERE team_id = %s` rather than piggybacking on the `teams` cascade. Added `test_run_ingestion_preserves_a_same_gameweek_instinct` / `test_run_ingestion_purges_a_stale_gameweek_instinct` to `test_ingestion.py` — the test gap that let this hide — and noted the correction in issue 13's own Comments.

`run_creator_ingestion` gained a required `team_id` parameter (the CLI passes `MY_TEAM_ID`) so each extracted Stance can be tagged with that team's current gameweek via `instincts.current_gameweek` (reused, not duplicated) — taken as a parameter rather than importing `MY_TEAM_ID` directly, so the ingestion module doesn't reach into the API layer. `gameweek` is nullable throughout: creator ingestion must not require team ingestion to have ever run first.
