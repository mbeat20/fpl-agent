## 1. Refreshing data is no longer a terminal-only act (ADR-0019)

The user's question was "every time I want to refresh the data, do I have to go through an agent?" The answer was already no — `fpl-ingest` is a CLI — but the ceremony was wrong for a weekly act, and there was a real hole behind it: **nothing recorded that a refresh had happened**, so no panel could say how old its data was.

Built:

| File | Role |
| ---- | ---- |
| `ingestion_runs` (schema.sql) | The ledger. Partial unique index = the lock. No FK to `teams` — the first FPL run *creates* that row, so a constraint there makes bootstrap impossible. |
| `ingestion/runs.py` | Lock, two-hour crash reaper, and freshness with a three-valued `source`. |
| `ingestion/jobs.py` | **One** definition of "a run". The CLI and the API both go through it. |
| `ingestion/cli.py` | Rewired — a terminal run lands in the same ledger, and can now be told the dashboard already has one in flight. |
| `POST /ingest/{kind}` · `GET /ingest/status` | 202 + background task; 409 while one is running. |
| `RefreshControl.tsx` | Header badge → panel. Billed source behind a confirm. |

**Verified live, not just tested:** a real FPL refresh through the endpoint took 97s (15 squad players, 380 fixtures, 652 pool, 133 outcomes, 38 deadlines, 20 clubs); an immediate second POST returned 409 carrying the holding run. 22 new tests.

Things that will bite you:

- **`freshness()` has three sources and they mean different things.** `proxy` (the data's own newest timestamp, used when no run is on record) is a *lower bound* — a run that found nothing new does not move it, and every run predating the ledger lands there. `none` is not "old". See ADR-0019.
- **The reaper is deliberately slow (2h).** Reaping a live run frees the lock and the next refresh starts a *second* concurrent pass over a billed pipeline. Too-eager is the expensive direction.
- **`uvicorn` here runs without `--reload`** (memory: an orphaned reload watcher was the port-8000 ghost process). So backend edits need a manual restart, and I lost twenty minutes to "why hasn't my change taken effect".

## 2. Five pages instead of two tabs

`App.tsx` held a two-value `useState<View>`, and the Team tab stacked eight panels of unrelated purpose in one 640px column — deadline triage, squad reference, plan tracking and creator discourse. Two of those panels are explicitly *not* about the user's team; `/creators/attention`'s own docstring says so.

Now: `Deadline` `/` · `Squad` `/squad` · `Coach` `/coach` · `Plan` `/plan` · `Discourse` `/discourse`, on a hand-rolled ~40-line history router (`router.ts` + `components/Link.tsx`). No new dependency: five flat routes need `useSyncExternalStore` and a `popstate` listener, not react-router.

**`useEndpoint.ts` is the load-bearing part.** The old dashboard put all eight fetches in one `Promise.all` behind one render gate that included `/team/suggestion` — the only read that can make a Claude call. Measured: the free, instant deadline countdown waited ~20 seconds for it, showing "Loading your squad" the whole time. Panels now load independently, and it has three states (loading / loaded-empty / failed) for the same reason `ChecklistItem` does.

Deadline is designed; Squad, Coach, Plan and Discourse are **faithful ports** of the existing panels and are still owed a design pass. `PlanPage` is the one to do first — see §5.

## 3. Four things the browser found that tests could not

1. **The 20-second block** above.
2. **Price movement listed all 17 squad players**, every direction, raw counts, with the interesting suffix (`-- price has already moved today`) truncated mid-word by CSS. Now `PriceRiskPanel`: three each way, the rest behind a disclosure, "moved today" as its own mark. The framing was also changed from a prediction to a **ranking** — the score is `net_transfers / ownership`, which approximates FPL's undocumented threshold rather than knowing it.
3. **The attention board repeated its own caveat verbatim on eight consecutive rows.** `consensus.py` writes that sentence *for the reasoning layer* (ticket 18: a phrase the model can quote beats a number it must interpret), so trimming it server-side would fix the screen by degrading the model's input. Fixed presentationally instead: rows are grouped by `movement`, the caveat is the group's heading, rows keep only their numbers. Twelve players now fit where four did.
4. **Themes were headed by unreadable ASR fragments.** Three-stage fix, in ADR-0021 — seed and label separated, a deterministic assembled `title` added, and the title's players ranked by distinctiveness rather than frequency. That last one needed two iterations: frequency put "Bruno Fernandes" in six of eight titles, and naive distinctiveness put `Chiao` and `Arne Slot` (a manager) there instead.

## 4. The lesson

Every one of those four had passed its tests, and three of them are *information design* failures rather than logic failures — a panel that is correct, cited, honest, and unreadable. **A screen no human has looked at is not finished, however green the suite is.** Ticket 29's clustering was verified against the live corpus and its output was still unusable as a heading, because "is the cluster right" and "does the panel communicate" are different questions and only one of them had been asked.

Related, and cheaper: **measure before building.** Ticket-style intuition said the transcript match rate was an ASR problem worth a fuzzy-matching pass. Five minutes of bucketing (ADR-0020) showed a fuzzy pass would misattribute about twenty-five Stances to recover ten. The measurement cost less than the code would have.

## 5. Where to pick up

1. **Design the Plan page.** `/team/roadmap` and `/team/roadmap/versions` are built, tested, and **fetched by nothing**. Roadmaps are versioned specifically so "last week's plan said something different" is answerable, and that question has never had a surface. Biggest gain available in what the app can show.
2. **Design Squad and Discourse properly.** Both are ports. Squad already pairs Instincts with consensus-on-instinct-players, which is ticket 13+19's actual question and used to be four panels apart.
3. **`/creators/themes` takes ~14 seconds.** All-pairs pgvector neighbours over 1,122 chunks. Fine as a background panel, poor as a page. Needs an index or a narrower window before the corpus grows.
4. **Run the integration suite.** Still not run since ticket 22 — ticket 25's plan validator has never been exercised by a real model, which remains the phase's biggest untested seam.
5. **Ticket 26** still waits on a cost ceiling from the user. So does authenticated FPL access, without which every affordability figure in a roadmap is an upper bound.
6. **Widen `_TOPICS`** if themes still read thin — four of eight currently resolve to "Captaincy". Closed list on purpose (ADR-0021).
