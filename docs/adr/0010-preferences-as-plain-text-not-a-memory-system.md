# Preferences are a plain text file, not a memory subsystem

The plan's Memory section implies a system that stores and retrieves user preferences (possibly per-context or vector-searched). Instead, Preferences (standing traits — see CONTEXT.md) live in a single flat file (e.g. `preferences.md`), loaded in full into every system prompt. Edited directly by the user or appended to when they say "remember: X". No schema, no extraction pipeline, no retrieval logic. This is deliberately decoupled from Horizon (how far out a Recommendation looks — this week vs. multi-week vs. season), which is never persisted: it's resolved live from whatever the question asks each time. Splitting these avoids the trap of needing per-horizon preference variants (e.g. "risk tolerance for 1-week vs 6-week") — Preferences stay small and horizon-independent by construction. Revisit if the list of preferences grows large enough that dumping the whole file into every prompt becomes wasteful or contradictory entries need reconciling.
