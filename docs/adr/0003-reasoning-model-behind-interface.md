# Reasoning model sits behind a thin interface, not a hardcoded provider call

Which reasoning model performs best for FPL recommendations is an open question the plan explicitly can't answer yet — there's no evaluation data. Rather than hardcoding one provider's API into the reasoning layer, it's accessed through a single internal interface (e.g. `reason(prompt, tools) -> Recommendation`), with one provider as today's implementation. This costs a small abstraction now in exchange for swapping models later being a new implementation rather than a refactor of every call site — useful both for comparing models against each other and for the multi-model-architecture learning goal. Data collection (Grok, for X access) is a separate concern from reasoning and isn't behind this same interface.
